# Claude Code Haha v0.5.47

> 本版本聚焦 Grok / OpenAI 兼容路径上的 **mid-stream 断流重试可感**，并与手动「停止」严格区分；修复桌面任务栏「清空已完成任务」因快照过严匹配失效的问题；并补齐 **会话 jsonl / queue-operation 内存防护** 与 **后台子代理僵尸状态清理**。**不**声称修复上游 60s 掐流本身。

## 问题背景

- Comic / 多项目在 `grok-4.5` 等 OpenAI 兼容上游上，约 60s 静默后出现  
  `OpenAI messages stream disconnected before completion`。
- **主因**：上游 / 网关掐流（非 Comic 仓库、非 desktop 默认 240s idle watchdog）。
- **0.5.46 次因**：断流已纳入 mid-stream **识别 + 重试**，但 `stream_retry` 对用户几乎透明（清掉横幅、不显示「正在重试」），长静默体感像卡死，也难和「点了停止」区分。
- **任务栏**：全部完成后点 X 清空，偶发无效；根因是 `resetTaskListIfMatches` 用 `isDeepStrictEqual` 全量比对磁盘 Task 与桌面 snapshot，description / owner / blocks 等字段漂移导致 `reset: false`，列表被 refresh 拉回。
- **会话膨胀 / sidecar 内存**：命令队列每次 `enqueue` / `dequeue` / `remove` / `popAll` 都会把 `queue-operation` 整行写入会话 jsonl；完成通知 remove↔enqueue 死循环或高频抖动时，可把单会话刷到 **约 2.4–2.7 GB / 数十万～近百万行**。sidecar 打开、恢复或索引该文件时 RSS 可到十几～二十几 GB，进程崩溃后后台子代理又收不到终态 `task_notification`，桌面 UI 仍显示「进行中」。

## 行为变更

### A. 自动断流重试（未点停止）

1. 上游 disconnect 且仍可安全重试时：丢弃本轮未提交流式碎片（保持 0.5.46 安全语义），**显示**琥珀色重试横幅：  
   - 标题方向：「连接中断，正在重试」/ attempt `i/max`  
   - 原因标签：`stream disconnect`（可附截断 errorMessage）
2. 重试期间：`chatState` 保持 thinking/running（**不是** idle）；停止按钮仍可用。
3. 重试成功：清横幅，正常继续。
4. 重试耗尽：终态 API Error（可带 retried N times）；停止按钮消失 / idle。

### B. 手动点击「停止」

1. **立刻** UI idle，**绝不**进入「断流重试」横幅（`stopGeneration` 清 `apiRetry`）。
2. 已在进行的 mid-stream 重试 / backoff 因 `AbortSignal` **不再发起下一轮**。
3. 视觉上：停止 = 用户主动结束；断流重试 = 系统自动恢复（琥珀色横幅且未 idle）。

### C. 清空已完成任务

- 完成集清空匹配改为 **id + subject + 全部 completed** 的语义比对；允许 description / owner / blocks / activeForm 等字段与磁盘不完全一致。
- 仍拒绝：数量 / id 不一致、存在未完成任务、同 id subject 已变（新周期或内容已改）。

### D. 会话内存防护（queue-operation / 超大 jsonl）

1. **默认不再持久化 queue-operation**  
   - `messageQueueManager` 默认不写 transcript。  
   - 仅当 `CLAUDE_CODE_PERSIST_QUEUE_OPS=1` 时写，且 **只写 enqueue**、content 截断约 200 字符、限速（约 1s 窗口最多 20 条）。  
   - `dequeue` / `remove` / `popAll` **永不落盘**。
2. **超大 jsonl 只读尾部**  
   - `SessionService` 超过 `maxFullJsonlReadBytes`（生产默认 50 MiB）不再整文件读入，只读 tail；窗口落在半截行时丢弃不完整行。
3. **退出错误截断**  
   - runtime exit detail 用户可见部分上限约 4 KiB，避免 Bun panic 整段刷进聊天 / 再撑内存。

### E. 后台子代理僵尸状态清理

1. CLI 进程异常退出或会话关闭时：对仍登记的 `activeBackgroundTaskIds` **合成** `task_notification`（`stopped`）并广播，桌面不再长期卡在「进行中」。
2. 停止已消失任务：识别 “No task found / already gone” 类失败，**不把 UI 又刷回 running**。
3. 桌面 `ToolCallGroup` / `chatStore`：嵌套子任务状态不再单独把父任务钉死在 running；停止失败路径与服务端合成终态对齐。

## 技术要点

| 区域 | 变更 |
|------|------|
| `withStreamRetry` | yield `stream_retry` 时附带 `attempt` / `maxRetries` / `retryDelayMs` / `errorMessage` |
| messages / QueryEngine / WS | 透传上述字段到 desktop |
| `chatStore` | `stream_retry` 写 `apiRetry`（`errorType: stream_disconnect`），丢弃本 attempt 碎片，保持 thinking；停止失败不再复活 running |
| `StreamingIndicator` + i18n | 断流专用 title / kind（中英日韩繁） |
| `resetTaskListIfMatches` | `completedTasksMatchResetSnapshot` 替代 deep-equal |
| `messageQueueManager` | `shouldPersistQueueOperation` 默认 off；限流 enqueue-only；`truncateQueueOpContent` |
| `sessionService` | `maxFullJsonlReadBytes` + `readJsonlTail` / 半行丢弃 |
| `conversationService` | `MAX_RUNTIME_EXIT_DETAIL_BYTES` 截断退出详情 |
| `ws/handler` | CLI exit / session close 合成 stopped background tasks；persist-fail 仍转发终态通知 |

## 明确不做

- 不防上游 60s 掐流；不改 Comic 仓库；不默认砍 desktop 240s idle。
- 不做 partial-stream 后仍强制重试（双工具执行风险）。
- **不**声称已从根上消灭「完成通知在内存队列里 remove↔enqueue」的全部抖动路径；本版优先切断 **jsonl 刷盘** 与 **崩溃后 UI 没收尾**。
- **不做**进程级 RSS 硬/软上限（可另开）。
- 本轮 **默认不自动触发远程 GitHub Release**；以本地 Windows 测试包 + PR 为准，远程发布另开指令。
- 已存在的历史超大 jsonl 仍建议手动删除/移走；本版只保护加载与后续写入，不会自动瘦身旧文件。
