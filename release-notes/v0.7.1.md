# Claude Code Haha v0.7.1

修掉一个会让会话**彻底无法发送消息**的缺陷，以及它的成因。两者同源：一条超大记录进了会话文件，之后所有相关读取都被判为不可用。

## 会话不再因超大记录而失效

**现象**：某个会话读了几张大图之后，**再也发不出任何消息**——不是偶发，是每次必失败。

**成因**：读取截图会把图片以 base64 存进会话文件。base64 会让体积膨胀约三分之一，所以**一张 6MB 左右的截图**，在文件里就已经超过 8MB 的单条记录上限。历史读取会跳过这条记录（这是对的，不能把它读进内存），但**跳过被升级成了硬失败**：元数据被判为"不完整"，于是"读取会话启动信息"直接报错——而发送消息必须经过这一步。诊断日志里能看到 `ws_user_message_failed` 正是卡在这里。

跳过一张图片**并不影响启动所需的元数据**：工作目录来自体积很小的 `session-meta` 记录，那条永远读得到。现在这类跳过不再中断会话；真正用来防"超大数值撑爆元数据"的 128KB 上限保持原样，仍会拒绝。

**同时修掉产生超大记录的成因**：扫描本机 97 个会话文件后发现，本应被截断到 50KB 的 `<persisted-output>` 记录，实际有 **12.6MB**。原因是**落盘失败时会原样保留未截断的内容**，使 50KB 的截断保护静默失效。MCP 那条路径早已正确处理同一失败，只有这一处没有。现在单条结果与"单条消息聚合预算"两条路径都会降级为内存截断。

截断只针对文本；**文档等结构化内容原样保留**，不会被替换成占位符——过大的是文本，丢掉文档只会造成信息损失。

## 说明

- 本次为修复版本，未改动界面，未改动 CLI 启动参数。
- **已存在的会话**：修复后可以正常发消息了；历史里那些超大图片记录仍会被跳过（不显示），这是有意的内存保护。若需要完整历史，需另行处理那些记录。
- 改动经两个独立子代理审核；审核发现的**结构化内容被丢弃**与**聚合预算路径同一缺陷**两处问题，已在本版一并修复。
