# Claude Code Haha v0.6.8

本次更新合并上游 **Claude Code v0.6.6**（触及 1219 个文件、122 个冲突文件），并在此基础上重新移植 fork 的会话与设置定制点。上游带来的是**引用历史会话**与**跨会话协作**两项核心能力，以及会话加载、历史滚动、搜索的一轮性能改造；fork 侧则修掉了合并过程中丢掉的定制功能，以及三个 MCP 免重启注入的缺陷。

## 上游 v0.6.6：引用会话与跨会话协作

- **引用之前的对话**：输入 `@` 可以搜索并引用历史会话，例如「参考 @登录方案 的结论，补充退出登录流程」。引用不会把整段历史复制进上下文，Claude 按需读取被引用会话的内容；点击消息里的引用可直接打开那段对话，原会话不会被唤醒。
- **跨会话聊天与控制**：可以让 Claude 新建独立会话并行推进任务，并在会话之间收发消息、等待状态变化、汇报结果（`ListSessions` / `ReadSession` / `CreateSession` / `SendSessionMessage` / `WaitSessions`）。新会话会出现在会话列表里，可以单独打开继续聊；其他会话发来的内容以带来源标注的普通消息显示。每组协作最多同时运行 3 个工作会话，其余排队；Git 项目里的工作会话使用独立 worktree。
- **性能**：大会话改为一次字节上限内整体加载、整体挂载，不再分页拼接，消除滚动跳动与丢行；`@` 搜索与会话清理移出请求线程，中文搜索不再让其他接口排队；索引重建期间不再在本地索引与全量扫描之间来回切换，侧边栏不再反复闪「使用标准历史」；新增接口耗时监控，慢请求记入诊断面板。
- **其他**：`AGENTS.md` 项目指令（默认仍优先 `CLAUDE.md`）；供应商预设可切换协议；Grok 4.7 及其快速档，推理强度按官方目录解析；SubAgent 卡片显示实际使用的模型；上下文用量环按已用比例填充。

## 合并中丢失的 fork 定制点：已找回

合并把部分文件整体取用了上游版本，fork 在这些文件里的增量改动随之消失。这类丢失不产生类型错误、不影响编译，**只有对应测试或人工比对才会暴露**。本次找回：

- **供应商兼容性徽章**。服务商卡片上「伪 `tool_use` 计数超阈值」与「thinking 不兼容」两个提示徽章整体消失——上游没有这两个徽章，所以合并时无声无息地没了。问题不只是少了个角标：`chatStore` 仍在累计这些计数，7 个语言文件的文案也都在，但**没有任何地方渲染**，于是「某供应商静默回落或吐出伪工具调用」这件事只剩下一次性提示，用户再也看不到持久状态。现已回植，并补上回归测试。
- **会话历史读取的有界元数据折叠**。会话子系统整体取用 fork 版后，上游这个「一次流式折叠同时得出启动元数据、列表摘要与自定义标题」的实现从未回植，导致三个本不该解析整份 transcript 的读取口被指回整文件读取——打开一个含若干 256 KB 记录的会话就会把整份文件读进内存。现已按上游实现回植（128 KB 元数据信封上限 + 按源版本失效的缓存），并保留 fork 必须随投影携带的字段。
- **元数据搜索的 JSONL 扫描兜底**。回植时被截成「只用索引，否则返回空」，丢掉了上游的扫描与排序兜底，索引不可用时会搜不到任何会话。
- **离开计划模式后的权限模式还原**（`prePlanPermissionMode`）。fork 有 17 处引用，合并后为 0——离开 plan 模式无法还原用户原本的权限模式。已完整恢复，并修掉一处「已清除」墓碑被 `??` 吞掉、导致旧值残留的问题。

## MCP 免重启注入：三个连接清理缺陷

「在设置里增删或改 MCP 服务器，运行中的会话立即生效，不必重启」这条路径上有三处缺陷，**同属一种形状：清理或合并用的键比真实身份更窄**。三处都是从上游继承而来（fork 与上游在该文件逐字节相同），不是本次合并引入。

- **连接缓存的键里混进了 `scope`**。代码库自己已经声明 `scope` 记录的是「定义来自哪里」（`.mcp.json` / `settings.json` / 插件 / 运行时注入）而非「连接是什么」——`areMcpConfigsEqual` 与 `hashMcpConfig` 都剥掉它，后者注释写得很明确：「把服务器从 `.mcp.json` 挪到 `settings.json` 不该触发重连」。只有缓存键没遵守这条。于是重连时按文件作用域去清，命中的却是 `scope: 'dynamic'` 下缓存的连接——**清不掉，旧连接及其子进程继续存活**。现已从键里剥掉 `scope`。
- **启动连接被「收养」进动态状态时被孤立**。上一条修好后，收养会**复用启动时那条连接**而不是新建第二条，孤儿随之消失。
- **资源工具每次重连永久重复**。重连会返回合成的 `ListMcpResourcesTool` / `ReadMcpResourceTool`，而各处合并只删 `mcp__<服务器>__*`——这两个名字没有该前缀，于是每次重连留下旧的、再追加一对，`appState` 与动态状态里的工具数组**每次 +2 且无上限**。模型看到的工具列表因为有去重所以是正确的，代价是内存持续增长。现改为按名字归并，重复应用成为空操作。

> 这三处的严重度受一个事实限制：CLI 进程是**每会话一个**，会话结束即退出，退出时会关闭所有连接（含孤儿）。所以它们是「长时间不关的会话里反复改动 MCP 配置」才会累积，不跨重启。修法是让缓存身份等于连接身份。

## 修复

- **`settings.test.ts` 等测试文件保留了上游用例却留着 fork 的导入**，导致四个用例引用未定义符号；已补回导入。
- **projector / coordinator 的测试文件带着上游用例**，而它们测的是合并刻意未采用的 worker/spool 架构（fork 保留批处理架构）。恢复为 fork 版本。
- **`sessions.test.ts` 的解析缓存用例指向了已改道的读取口**：`getSessionWorkDir` 现在走有界投影（用 `fs.open` 而非 `fs.readFile`），三个用例断言在投影根本不做的读取上，其中一个还退化成 `0 === 0` 的空转。已改指仍在用该缓存的读取口，并补回内容断言。
- **两个测试脚手架缺陷**：一个用 `stdin: new Blob([...])` 喂输入，在 Linux 上子进程收不到字节（实测 Blob → 0 字节 stdout，管道 → 173 字节），另一个依赖 shebang 脚本在 Windows 上无法被 `spawn`。已分别改用管道与显式运行时，两个平台均通过。
- **会话协作分页的用例期望早于上游自己引入的页数上限**（`COLLABORATION_READ_MAX_PAGES = 8`），130 轮的期望不可能达成。已按该常量断言「链式读取所服务的轮次连续且为最新 80 条，并正确报告到达上限」，并把游标长度不变量移到真正产出它的存储层。
