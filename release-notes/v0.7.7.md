# Claude Code Haha v0.7.7

修复一个团队启动的**死路**：批准一个待审核的团队计划时，如果领队的 CLI 没有在运行（重启应用后、或空闲会话的 CLI 已被回收），启动必然失败，且界面上没有恢复手段。无上游合并。

## 团队：批准不再要求「先手动把会话跑起来」

**现象**：批准团队计划时报 **「Team leader must be connected before launching」**，点「重试」退回「待审核」，再批准还是同一个错——计划卡在死循环里。

**根因**：批准走的是 HTTP 路由，它**从不拉起领队的 CLI**。而 CLI 只在两种时机启动：你往会话里发消息，或空会话的预热。所以一个停在「待审核」的持久化计划，在下面这些情况下必然批准失败：

- 重启应用后打开旧会话（非空会话打开时**不预热** CLI）；
- 会话闲置超过预热回收时限，或渲染端断连 30 秒后 CLI 被停掉；
- 服务端重启，所有 CLI 进程随之退出。

**修复**：批准前先把领队拉起来——复用 `send_agent_message`、`/btw` 侧问同一套「按需启动 CLI」机制。附带两个安全边界：

- **只有确实在「待审核」、且属于请求会话的计划**才会拉起进程；伪造身份、过期请求、草稿或已取消的计划不会误启动。
- 启动被拒（如工作目录不存在、供应商变更需重开会话）时把**可操作的原因**透出，而不是笼统报错；计划保持「待审核」，修好条件后可直接再批准。

启动日志现在会区分来源（`team_approval` / `agent_message`）——此前统一记成 `agent_message`，正是这个歧义让本问题难以定位。
