# Claude Code Haha v0.7.2

修掉两类会让会话**彻底无法继续**的缺陷。两者的共同点：一条坏记录留在会话历史里，而每一轮请求都要重发整个历史，于是一次失败变成永久失败。

## 一、超大记录不再吞掉消息

**现象**：读了几张大图的会话，那些图片消息在界面上消失；严重时整个消息列表变空。

**成因**：读图时同一张图的 base64 被**存了两遍**——一份在发给模型的 `message.content` 图片块里，一份在 `toolUseResult.file.base64` 里。所以一张约 4MB 的截图就产生约 8MB 的记录，超过 8MB 的单条上限后被历史读取整条丢弃。而历史一旦被判为不完整，界面会把消息列表**整体置空**。

**修复**：

- 写入侧不再重复存那份 base64（它没有任何消费者：桌面端只读 `answers`/`questions` 和 `backgroundTaskId`；CLI 只读 `originalSize`/`count`/`cells`/`numLines`）。新会话不再累积这份重复。
- 读取侧对仍然超限的记录先**瘦身再决定**：体积来自无用字段的就保留，来自其他原因（例如纯文本）的仍按原逻辑丢弃——不会凭空造内容。

## 二、畸形的图片 URL 不再废掉会话

**现象**：某个会话读到一张图片后**再也发不出消息**，`/compact` 也一并失败。

**成因**：MCP 工具返回的图片 URL 尾部被拼进了一段带引号的中文说明：

```
https://…/qrcode/m_qwe3.png "扫描此二维码测试游戏"
```

`new URL()` 会把尾部百分号编码后**接受**它，所以本地一路无感，直到网关以「参数非法」拒绝整个请求。这条记录在历史里，于是每轮必失败——连同压缩请求。

**修复**：转换层发现 URL 无法转发时，**降级为文本提示**（保留原始 URL 便于定位），而不是原样透传。base64 图片不受影响。

## 三、变更视图不再被单次编辑关闭

**现象**：某个会话的「变更」视图永久不可用，接口返回 413。

**成因**：编辑工具会把**整份编辑前文件**存进 `toolUseResult.originalFile`（用于回滚）。对 60KB 文件的一次编辑就产生约 67KB 的工作区记录，而其 `tool_result` 只有 174 字节——超过 64KB 上限后，变更视图被判为不完整并永久禁用。

**修复**：剥离 `originalFile`。变更视图的状态、行数与 diff 全部来自 `old_string`/`new_string`，不读这个字段。

## 说明

- 本次为修复版本，未改动界面，未改动 CLI 启动参数。
- **已存在的会话**：新版本会正常读取并保留上述消息（不再丢弃）。此前版本已经吞掉的消息，需要该记录仍在文件中才能恢复显示。
- 一个已知但**未处理**的同类缺口：`NotebookEdit` 的 `original_file`/`updated_file`（完整的 notebook 前后内容）也是无消费者的重复存储，但未被本次瘦身覆盖。它在本地全部会话中**零出现**，属潜在问题。
- 改动经三个独立子代理对抗性审核：其中发现并修复了一处**由本次改动引入的回归**（剥离图片 base64 后，CLI 的行内渲染会因 schema 校验失败而整行消失）；另有一处计数口径错误已更正。
