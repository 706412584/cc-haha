# Spark2 GameUI 视觉设计与精修

本技能解决“页面应该如何组织、为什么这样更清晰美观”，并将结论直接落实到 Spark2 C# GameUI。

它不替代：

- [`ui-layout-api`](../ui-layout-api/SKILL.md)：GameUI 布局 API、对齐、Flow/Flex、Grid 和响应式实现。
- [`debug-tools`](../debug-tools/SKILL.md) / [`client-only-debug`](../client-only-debug/SKILL.md)：启动和连接真实客户端。
- [`ui-export-real-loop`](../ui-export-real-loop/SKILL.md)：双端构建、部署、全页 Runtime MCP 和资源闭环验收。

默认链路：

```text
ui-visual-design（信息架构与视觉决策）
  → 直接 C# GameUI / ui-layout-api（实现）
  → debug-tools 或 client-only-debug（运行）
  → Runtime MCP 截图与 UI tree（视觉 QA）
  → ui-export-real-loop（需要全项目真实验收时）
```

布局器、旧版 UI、Figma 或截图可以作为参考输入，但不是必经实现层。除非用户明确要求操作 layout-editor，否则直接修改项目拥有的 GameUI C# 源码。

## 1. 先区分“能显示”和“设计正确”

以下证据只能证明工程状态，不能单独证明界面美观：

- 编译通过；
- root 填满 viewport；
- 无越界/重叠诊断；
- 控件能找到、按钮能点击；
- 图片和 NineSlice 能加载；
- 页面截图文件存在。

视觉通过还必须检查：

1. 玩家进入页面后第一眼是否知道当前目标。
2. 是否只有一个明确的主操作，次要操作没有争抢权重。
3. 信息是否按“身份/状态 → 核心内容 → 操作 → 辅助说明”分层。
4. 字号、图标、触控尺寸在真实运行截图中是否可读可点。
5. 背景主景是否被不必要的大面板遮住。
6. 卡片、边框、颜色、按钮、图标是否使用一致的视觉语言。
7. 默认、选中、锁定、空、加载、成功、失败和弹窗状态是否清楚。

禁止用“0 error”“20 页都有截图”“结构完整”替代视觉结论。

## 2. 视觉任务预检

开始编辑前，按顺序建立事实：

1. 读取项目规则和相关 GameUI 源码，确认真正的 authoring source。
2. 查找现有页面壳、主题 token、组件、按钮皮肤、NineSlice 和资源选择模式，优先复用。
3. 确认设计分辨率、`ScaleMode`、启动窗口、截图尺寸和 `SafeZonePadding`。
4. 查看当前真实截图；若客户端未运行，先使用已有最新截图做初步判断，但完成前仍须采集当前运行时截图。
5. 若用户提供红框、参考图或旧版页面，把它当作设计证据；不要只从代码名推断视觉效果。
6. 若文件会被生成器覆盖，先确认持久化边界。默认把耐久逻辑放进项目拥有的 GameUI 源码、共享组件或包装层，不把长期设计依赖建立在易覆盖的导出补丁上。

### 视觉来源优先级

从高到低：

1. 用户当前明确要求和标注；
2. 当前真实客户端截图；
3. 项目已有成熟页面、组件和真实资源；
4. 用户指定的旧版/参考图；
5. 项目设计文档和 token；
6. 通用游戏 UI 规律。

不要把某一页风格强行复制到所有页面。复用其结构规律和组件语言，而不是照抄构图。

## 3. 先写一页视觉契约，再写控件

每个页面先在工作说明中明确以下七项，不需要为此新建文档：

```text
玩家任务：进入此页要完成什么？
主视觉：第一眼看什么？
主操作：唯一最重要的 CTA 是什么？
次要操作：最多哪些入口需要同屏？
核心信息：必须首屏读到什么？
滚动信息：什么可以放进 ScrollView？
状态：默认/选中/锁定/空/加载/错误/成功/弹窗有哪些？
```

如果说不清主操作和核心信息，先调整信息架构，不要开始堆 Panel。

## 4. 选择页面原型

### 4.1 海报/入口页

适用：标题、登录、章节开场。

- 全屏主视觉；
- 低信息密度；
- 标题、副标题、单一主 CTA；
- 设置、区服、版本等退居边缘；
- 不要用多张卡片切碎背景。

### 4.2 HUD/主页

适用：洞府、角色主页、战斗大厅。

- 顶部只保留高频身份与资源；
- 中央主视觉保持完整；
- 功能入口分组放在边缘，不围成无层级的按钮墙；
- 当前任务/收益使用一个轻量承载区；
- 底部主导航只承载稳定一级栏目。

### 4.3 列表/管理页

适用：背包、任务、邮件、排行榜、商城。

固定顺序优先：

```text
标题/返回 → 总览 → 筛选/Tab → ScrollView/Virtualized content → 选中详情或固定操作
```

大量物品使用 `TrueGrid` / 虚拟化列表，不用手算每个格子坐标。筛选、网格和详情必须共享一套列宽、间距和选择状态。

### 4.4 角色/灵宠展示页

- 角色或灵宠是视觉焦点；
- 关键属性贴近主体，但不要覆盖脸部和轮廓；
- 养成区按“当前状态 → 消耗 → 提升结果 → 主操作”组织；
- 阵容/列表放到次级区域或滚动区；
- 未出战与选中状态必须有明确差异。

### 4.5 制作/炼丹页

- 核心对象（丹炉、锻造台、配方）占主视觉；
- 材料槽、数量、成功率和预期产物形成一条阅读路径；
- 主操作靠近结果，不散落多个同权按钮；
- 制作中切换为明确的进度与完成反馈，而不是只改一行文字。

### 4.6 地图画布页

- 地图是内容，不是卡片背景；
- Marker 使用数据驱动相对坐标；
- 锁定、当前、已完成、推荐区域有不同状态；
- 点击 Marker 后用浮层/底部详情展示信息；
- 禁止用大矩形按钮阵列冒充地图地点。

### 4.7 挑战/副本页

- 当前层/关卡、敌人、门槛、奖励、主挑战按钮形成清晰顺序；
- 当前目标权重大于历史列表；
- 扫荡、排行、奖励预览属于次级操作；
- 锁定原因必须可读。

### 4.8 对话/设置/说明页

- 聊天使用频道、消息流、输入区三段结构；
- 设置按主题分组，不用一张超长说明卡；
- 说明页控制文本行宽与段落节奏；
- 弹窗统一放在 overlay stack，不参与主内容 Flow。

## 5. 直接 GameUI 页面骨架

优先使用“固定壳 + 流动内容 + 独立覆盖层”：

```text
Root（全屏背景，可延伸到 Safe Zone 外）
├─ BackgroundLayer（无交互，最低 ZIndex）
├─ SafeContent
│  ├─ Header（固定）
│  ├─ Content（Flow / Scroll / Grid，消化剩余空间）
│  └─ PrimaryAction / BottomNav（按页面类型固定或流动）
└─ OverlayLayer（Mask / Modal / Toast / Guide）
```

实现约束：

- 2 个以上普通内容子项优先 `FlowVertical()` / `FlowHorizontal()`，不要逐项计算 Y。
- 页面主区域优先 `.HeightGrow(1)` / `.WidthGrow(1)` 消化剩余空间。
- 长内容使用 `ScrollableVStack`、ScrollView 或虚拟化列表。
- 背包/商品/技能墙使用 `TrueGrid`；列数和间距来自共享参数。
- 绝对定位只用于地图 Marker、HUD 悬浮按钮、角色立绘装饰、粒子和明确的空间构图。
- 使用 Margin 定位时必须显式设置符合设计意图的水平/垂直对齐，避免继承默认 Center；只有以左上角为原点时才使用 `AlignLeft().AlignTop()`，右侧、底部或居中元素使用对应的 Right/Bottom/Center 对齐。
- 背景、内容、浮层分开管理 `ZIndex`；透明点击层不得遮挡下层交互。
- 重要 UI 放在 `SafeZonePadding` 内，背景与非交互装饰可以全屏。

## 6. 设计 token 与组件复用

先查项目现有 token/组件；已有时禁止另起一套。

多页共用且项目尚无规范时，才建立最小 token 集：

- `Typography`：Display / PageTitle / SectionTitle / Body / Caption；
- `Spacing`：使用 4 或 8 的有限阶梯，不给每个节点发明新间距；
- `Radius`：Small / Medium / Large；
- `Colors`：TextPrimary / TextSecondary / Accent / Success / Warning / Disabled / Overlay；
- `Chrome`：HeaderHeight / BottomNavHeight / PagePadding；
- `Assets`：PrimaryButton / SecondaryButton / Panel / ItemFrame 的资源和 NineSlice 参数。

只有一个页面、一个用途时，不为抽象而创建全局 design system；在局部复用常量即可。

### 组件优先级

1. 项目现有共享组件；
2. 项目现有成熟页面中的局部模式；
3. GameUI 语义组件与 Flow/Grid；
4. 项目真实图片和 NineSlice；
5. 最后才是纯色/渐变占位。

同一个页面中相同层级的按钮必须复用同一资源、尺寸和切片。颜色变化表达语义状态，不用于制造无意义的“花哨”。

### 全局按钮与面板资源契约

全局定义不是“所有按钮只准一种皮肤”，而是按语义建立有限集合：

```text
PrimaryButton   唯一主操作
SecondaryButton 次级操作
DangerButton    不可逆或危险操作
Panel           页面主承载
ItemFrame       列表/格子轻承载
Modal           弹窗承载
```

每个定义统一资源路径、正常/按下/禁用状态、默认尺寸、Padding、文字样式和 NineSlice 参数。页面只能选择语义角色，不得复制路径和切片数字后局部变种。已有项目级 `UiTheme`、`UiAssets`、`UiChrome` 或等价类型时必须复用；项目尚无共享实现且资源只使用一次时，保留页面局部常量，避免过度抽象。

新增或替换共享资源时要扫描所有引用页面，并在至少一个小尺寸、横向拉伸、纵向拉伸和双向拉伸实例中做实机检查。全局资源变更属于跨页视觉变更，必须执行受影响页面截图回归。

## 7. 字体、物理尺寸和密度

不能只看设计坐标中的 `FontSize`。先计算当前运行时缩放，再看截图中的真实像素。

例如 `MatchHeight`：

```text
runtimeScale = screenshotHeight / designHeight
runtimeFontPx ≈ designFontSize × runtimeScale
runtimeControlPx ≈ designControlSize × runtimeScale
```

检查目标：

- 正文在截图中应稳定可读，通常不要低于约 16px 的可见高度；
- 高频正文和关键数值应接近 18–22px 的可见高度；
- 页面标题应明显高于正文，但不能挤压主内容；
- 主要触控目标在运行截图中至少约 44×44px，按钮之间有防误触间距；
- 不靠把所有字号一起放大解决层级问题，应同时调整信息数量、行高和容器节奏。

这些是检查起点，不是替代截图判断的死规范。自定义字体的字面高度、笔画密度和中英文混排可能需要额外校正。

### 密度预算

- 一屏只保留当前任务必需信息；
- 同一数据不要在标题、卡片和底栏重复三遍；
- 主内容区不要每行再套一层不透明卡片；
- 一般不超过“背景 → 主承载面板 → 内容项”三层视觉承载；
- 大面积面板优先轻透明或使用与背景构图匹配的 NineSlice，避免遮住主景；
- 辅助说明进入次级文字或展开区，不与核心数值同权。

## 8. 游戏资源与背景构图

资源使用前必须实际读取图片，确认语义、尺寸、透明通道和边缘，不按编号猜图标。

- UI 图片放在 `ui/image/**`，C# 从 `image/...` 引用。
- 面板/按钮优先 NineSlice，实机验证四角、边缘和中心。
- 背景先确定主景、人物、建筑和留白区，再放内容；不要先铺满卡片后才看背景。
- 角色脸部、武器轮廓、地图路径和核心建筑属于保护区。
- 图标必须表达真实功能；找不到合适资源时用明确占位并记录，不用 emoji、文本符号或错误语义图标冒充最终资源。
- 需要新资源时遵循项目资源生成策略；生成后验证真实格式、尺寸和 Alpha。

## 9. 状态设计

每个交互控件至少考虑：

- normal；
- selected/active；
- pressed（引擎支持时）；
- disabled/locked；
- loading；
- success/error feedback。

每个数据页面至少检查：

- 正常数据；
- 空列表；
- 未解锁；
- 资源不足；
- 长文本/大数字；
- 弹窗开启；
- 内容超出一屏。

状态差异不能只依赖颜色；同时使用文字、图标、透明度、边框或位置变化。禁用态仍要能读出“为什么不能操作”。

## 10. 截图驱动视觉 QA

修改前先保存 baseline；每个完整轮次集中修改后统一运行和截图，不要每改一个数就打断用户。

运行时证据顺序：

1. `debug.ping` / `debug.list_tools`；
2. `debug.capture_screenshot`；
3. `ui.snapshot`；
4. `ui.find` / `ui.get_rect` 定位问题控件；
5. 修改后同 viewport、同页面、同状态重新截图；
6. 对关键页面做 baseline/current 对比；
7. 有交互的页面额外截选中、弹窗、锁定或错误状态。

必须分别检查：

### 全页构图

- 第一视觉焦点；
- 上中下节奏；
- 左右平衡；
- 背景保护区；
- 主 CTA；
- 空白是否有意图。

### 局部细节

- 字体、字重、换行、截断；
- 组件内外间距；
- 图标尺寸、语义和锐度；
- NineSlice 变形；
- 半透明边缘和 Alpha 光晕；
- 选中/禁用/锁定状态；
- 触控 rect。

`ui.snapshot` 用于证明结构、可见性和 rect；截图用于判断最终视觉。两者冲突时以截图为最终表现证据，再用 tree 定位原因。

### 三层质量门

每轮视觉交付按三层验收，低层证据不能替代高层：

1. **静态布局审计**：资源路径集中度、NineSlice 参数合法性、普通多子项是否使用 Flow/Grid、显式对齐、重复按钮皮肤、明显绝对坐标堆叠和触控状态完整性。
2. **运行时几何与缩放审计**：基于 `rect_px` 检查父子越界、兄弟非预期重叠、Safe Zone、触控矩形、透明点击层，并执行等比/更宽/更窄/目标设备 viewport 矩阵。
3. **同状态像素回归与人工视觉审查**：锁定相同构建配置、SDK/引擎/渲染后端、viewport、页面、fixture 数据、locale、字体和状态，分别记录 baseline/current 构建标识后比较；然后由人工判断构图、层级、资源语义、字体和背景保护区。

自动审计适合发现确定性错误；“好不好看”“图标是否语义正确”“主次是否清楚”仍必须看真实截图，不能伪装成单一数值分数。

### 像素级回归契约

像素 diff 前必须锁定：

```text
build configuration / SDK-engine-renderer / viewport / pageId / state / fixture data / locale / font / resource readiness
```

baseline 与 current 可以来自变更前后的不同构建，但必须分别记录构建标识或提交；除待审视觉代码/资源外，其余上述条件保持一致。

规则：

- 静态页面允许全页像素 diff，同时保存 baseline、current、diff 图、差异像素比例、最大颜色距离和主要差异区域。
- 动画、粒子、视频、时间、随机头像、异步远程图等非确定区域必须固定输入、等待稳定后截图，或使用明确 mask/region diff；禁止简单提高全页容差掩盖真实回归。
- 文本抗锯齿和渲染平台差异可使用小范围颜色容差，但布局位移、裁切、白块和资源缺失必须保持敏感。
- 动态页面优先断言关键区域截图、控件几何、文本与状态，不强求全页零差异。
- diff 超出项目阈值时必须打开差异图，结合 `ui.get_rect` 定位；不能只根据百分比自动判定视觉优劣。
- baseline 只能在确认设计变更正确后显式更新，禁止测试失败时自动覆盖；更新需记录页面、状态、viewport 和变更原因。
- 没有项目历史数据时不虚构“通用合格阈值”。先保存稳定基线和差异报告，再根据抗锯齿噪声与真实缺陷样本制定项目阈值。

### 必测状态与边界

除默认态外，按页面能力覆盖：

- 空、加载、错误、离线/超时、未解锁、禁用、资源不足；
- 选中、按下、成功反馈、Toast、Modal、遮罩、返回；
- 最长本地化文本、换行/截断、超大数值、0 和负值；
- 列表最少/最多数据、滚动到底、虚拟化复用和返回后的滚动位置；
- 多次进入退出后的事件订阅、旧控件失效和重复触发；
- 图片加载失败、错误格式、透明边缘、低清放大和裁切；
- 自定义字体加载失败时的 fallback、字宽变化和中英文混排。

### 性能与输入补充

视觉正确但运行卡顿或误触仍不算完成。复杂页面同时关注：

- 节点数量、大列表是否虚拟化、滚动是否稳定；
- 大面积半透明层和重复背景造成的过绘；
- 每帧布局重算、重复图片解码或页面切换时整树重建；
- Overlay/Modal 的 ZIndex、输入穿透、焦点和遮罩关闭路径；
- 点击图标子节点时父按钮是否只触发一次；
- 页面销毁后旧节点、订阅和 Runtime 调试映射是否失效。

性能问题先测量再优化；不要为了降低节点数牺牲正确层级，也不要在没有基线时做微优化。

## 11. 问题等级与完成标准

- `P0`：页面无法使用、核心操作不可达、严重遮挡或裁切。
- `P1`：主次错误、关键信息不可读、背景/主视觉被破坏、主要状态缺失。
- `P2`：密度、间距、字体、资源、响应式或组件一致性明显有问题。
- `P3`：不阻断交付的细节润色。

视觉精修只有在以下条件满足时才能报告完成：

- 当前真实客户端截图已打开并检查；
- 页面主目标和主 CTA 清楚；
- 没有未解决的 P0/P1/P2；
- 关键文字和触控目标在实际 viewport 可读可点；
- 背景、面板、按钮、图标和字体形成一致语言；
- 默认态及至少一个关键交互/异常态已检查；
- UI tree 没有明显越界、遮挡或无意义重叠；
- 若修改 C#，Client-Debug 与 Server-Debug 都通过；
- 若涉及多页/导出资源，继续按 `ui-export-real-loop` 完成全页真实闭环。

## 12. 禁止事项

- 禁止把“无报错”写成“视觉通过”。
- 禁止只看代码或节点树，不看真实截图。
- 禁止为了修一个页面整页重写或统一套模板。
- 禁止为每段文字套卡片、为每个按钮换不同颜色/皮肤。
- 禁止用大量绝对坐标实现普通列表和表单。
- 禁止通过整体拉伸、任意 Margin 或增大 root 掩盖分辨率问题。
- 禁止把 Web/Figma 的 DOM/CSS 假设直接套到 GameUI。
- 禁止让布局器预览替代 Spark2 客户端结果。
- 禁止用错误语义图标、emoji、纯文本序号或代码绘图冒充已有真实资源。
- 禁止在没有检查 authoring ownership 时把长期修复写进会被覆盖的生成文件。
