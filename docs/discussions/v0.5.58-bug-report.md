# v0.5.58 Bug Report — 2026-08-16

## Bug 1: `TaskUpdate` 报错 `feature is not defined`

### 严重程度
**高** — 任何包含 3+ 个 task 的任务列表，在最后一个 task 完成时 `TaskUpdate` 调用会直接抛出 `ReferenceError`，导致任务状态更新失败。

### 位置
`src/tools/TaskUpdateTool/TaskUpdateTool.ts` 第 331-332 行

### 根因
代码中使用了 `feature('VERIFICATION_AGENT')` 和 `getFeatureValue_CACHED_MAY_BE_STALE('tengu_hive_evidence', false)`，但这两个符号都没有 import。

```typescript
// 第 331-332 行 — 缺少 import
if (
  feature('VERIFICATION_AGENT') &&  // ← ReferenceError: feature is not defined
  getFeatureValue_CACHED_MAY_BE_STALE('tengu_hive_evidence', false) &&  // ← 同样未导入
  ...
)
```

### 触发条件
1. 非 agent 子线程（`!context.agentId`）
2. 最后一个 task 被标记为 `completed`（`statusChange?.to === 'completed'`）
3. 任务列表 ≥ 3 个 task
4. 没有 subject 包含 "verif" 的 task

### 缺少的 import
```typescript
import { feature } from 'bun:bundle'
import { getFeatureValue_CACHED_MAY_BE_STALE } from '../../services/analytics/growthbook.js'
```

### 影响
这是 v0.5.4 上游合并时引入的 verification nudge 逻辑，但 import 在合并冲突解决中被遗漏。所有使用 TaskUpdate 完成 3+ task 列表的场景都会报错。

## Bug 2: Bash 后台任务无法手动停止，重启 IDE 后仍显示运行中

### 严重程度
**中** — 影响用户体验，后台任务卡在 running 状态无法清理，重启也无法恢复。

### 症状
- 点击停止按钮无响应
- 重启 IDE 后，Activity 面板中该任务仍显示 running
- 已确认的原生进程不存在，但 UI 状态未同步

### 根因分析

**链路 1 — 停止按钮无响应：**

`chatStore.stopBackgroundTask` (chatStore.ts:2717) 有一个「防重复」守卫：
```typescript
if (!task || task.status !== 'running' || session?.stoppingBackgroundTaskIds?.[taskId]) return
```

如果 `stoppingBackgroundTaskIds` 已经包含该 taskId（例如前一次停止请求未清理），则后续点击停止按钮都会被静默忽略。

问题在于 `stoppingBackgroundTaskIds` 只有在以下情况才会被清理：
- `stop_background_task` WebSocket 响应返回后，由 `handleBackgroundTaskStatus` 更新 task 状态
- 如果 WebSocket 消息丢失（例如网络断开），`stoppingBackgroundTaskIds` 永远不会被清理

**链路 2 — 重启后仍显示 running：**

会话恢复时，`backgroundAgentTasks` 通过以下路径重建：
1. `loadHistory` → `fetchAndMapSessionHistory` → 从 transcript 消息中提取 `background_task_status` 事件
2. `mergeBackgroundAgentTaskRecords` 合并恢复的 task 记录

关键问题在 `mergeBackgroundAgentTaskRecords` (chatStore.ts:5456)：
```typescript
// 第 5486-5491 行
if (
  existing?.status === 'running' &&
  task.status !== 'running' &&
  task.updatedAt < existing.startedAt
) {
  return tasks  // 保持 running 状态，丢弃更新的非 running 状态
}
```

这个守卫的本意是防止旧的非 running 事件覆盖新的 running 状态，但副作用是：如果 kill 通知的时间戳比 start 早（在 transcript 中排序靠前），terminal 状态会被丢弃，任务永远卡在 running。

**链路 3 — 进程已死但 UI 显示 running：**

`stopTask` (src/tasks/stopTask.ts:38) 在 kill 前检查 `task.status !== 'running'`，如果 Desktop 端恢复会话时把 task 状态标记为 running，但服务端进程中该 task 实际上已经不存在（进程已退出），则 `stopTask` 会抛出 `not_running` 错误，但 Desktop 端的 `stoppingBackgroundTaskIds` 已经被设置，且不会被清理。

### 建议修复方向
1. 给 `stoppingBackgroundTaskIds` 加超时清理（例如 30 秒后自动清除）
2. 在 `stopBackgroundTask` 中，如果 WebSocket 发送失败，立即清理 `stoppingBackgroundTaskIds`
3. 在 `mergeBackgroundAgentTaskRecords` 中，对终端状态（killed/completed/failed）的任务，即使时间戳较旧也应覆盖 running 状态
4. 会话恢复时，对 running 超过一定时间（如 24 小时）的 bash 任务自动标记为 killed
